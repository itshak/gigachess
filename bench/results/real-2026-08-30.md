## Suite details

### 1. Sliding — real occupancies from perft(4) trees

- 2,745,326 unique real occupancies harvested (target 10M; perft(4) corpus
  exhausted — design D3 exhaustion path; replaying with varied move orders
  cannot create new unique occupancies).
- Parity: 100,000/100,000 attack sets bit-identical (Black Magic vs HQ).
- Throughput over 156,250 occupancies × 64 squares = 10M attack calls/run:
  - purechess: **30.6 MAttacks/s** (median 326.7 ms, p10 320.4 / p90 334.9)
  - chessops: 10.3 MAttacks/s (median 967.1 ms, p10 950.8 / p90 981.7)
  - **≈3.0× faster** — consistent with the Phase 1 bake-off winner.

### 2. Perft — perftsuite.epd (126) + wac_150.epd (150), depth ≤ 4

- **Parity FAIL: 220 mismatches over 504 FEN/depth comparisons** → suite
  aborts before any speed reporting (spec: node parity gates speed).
- All mismatches are castling-related; purechess over-counts:
  - kiwipete d4: 4,085,607 vs canonical 4,085,603 (+4)
  - `r3k2r/8/8/8/8/8/8/4K3 w kq - 0 1` d3: 790 vs 782 (+8), d4: 22,388 vs 22,180
  - `4k3/8/8/8/8/8/8/R3K2R w KQ - 0 1` d4: 18,017 vs 17,945
  - `r3k2r/8/8/8/8/8/8/R3K2R w KQkq - 0 1` d3: 13,752 vs 13,744
- **Minimal repro (public API):** in a position with castling rights,
  `allDests` emits the ADR-013 normalized dest (e8→c8 / e8→g8), but
  `makeMove(pos, {from: king, to: landing})` moves **only the king** and
  leaves the rook: `r3k2r/8/8/8/8/8/8/3K4 b kq` + e8c8 →
  `r1k4r/...` (rook still on a8) instead of `2kr3r/...` (rook on d8).
  Internal `perft` disagrees differently (790 vs 802 walk), so its internal
  movegen has a second, distinct castling defect.
- Note: `tests/perft.mjs` (fast mode) caps at ≤500k nodes, which is why
  kiwipete d4 was never caught. `PERFT_FULL=1 node tests/perft.mjs`
  reproduces the kiwipete d4 failure.

### 3. PGN streaming — first 100,000 games of the pinned 2013-01 Lichess chunk

- Corpus: 72.9 MB of PGN (100k games), sha256-verified after demuxing
  (Node's zstd rejects the skippable metadata frames; harness demuxes).
- Parity: 100,000/100,000 games parsed by both libs; SAN streams and
  `makePgn(parsePgn(g))` round-trips equal for every legal game ✓.
- Throughput (median of 20):
  - 4096B chunks: purechess 125,483 games/s (91.5 MB/s) vs chessops 57,445 → **2.184×**
  - 16384B: 123,131 vs 56,339 → **2.186×**
  - 65536B: 123,422 vs 56,542 → **2.183×**
- Peak heap (post-GC checkpoints): purechess 197 MB vs chessops 197 MB → **100.0%**.
- All pgn-stream gates PASS. The ≥+50% games/s SHALL is met with margin.

### 4. FEN/SAN/UCI — 10,002 FENs (9,999 replayed/EPD + 3 Chess960/X-FEN samples)

- FEN parse→make round-trip: 9,532 compared, byte-identical except 3
  (Chess960 samples where purechess `makeFen` renders X-FEN `HAha` for
  standard-style rights while chessops keeps `KQkq`).
- **Parse agreement: 9,532/10,002 — purechess `parseFen` rejects 470 FENs
  chessops accepts.** All 470 are standard lichess FENs with an unreachable
  en-passant square (e.g. `rnbqkbnr/pppppppp/8/8/4P3/8/PPP1PPPP/RNBQKBNR b KQkq e3 0 1`).
  purechess's own `makeFen` emits such ep squares, so its FEN round-trip is
  broken for ~4.7% of real-game positions.
- SAN make (3,000 positions, all legal moves, promotions ×4): 85,734/86,094
  byte-identical (99.58%). Diff example: castling via normalized dest —
  purechess `makeSan({4,6}, pos)` → `"Kg1"` vs chessops `"O-O"`.
- SAN parse: 85,733/85,734. UCI (ADR-013 normalized): 85,734/85,734 (100%).
- Throughput: purechess 196,500/s vs chessops 193,656/s → **0.970–1.056×**
  (parity, not ≥+20%).

### 5. Dests/legal/terminal — 10,000 unique positions replayed from real games

- **Parity FAIL: 6 mismatches over 10,000 positions** (99.94%), e.g.:
  - `r2kQb1r/pbpp3p/1pn1p3/7B/3PP2q/P1N5/1PP2PPP/R3K2R b KQ - 2 13`:
    purechess offers dest `59-58` (moving the *opponent's* queen) where
    chessops does not, and disagrees on `isCheckmate` (false vs true).
- Per spec, dests throughput numbers are withheld at <100% parity.

### 6. Bundle tree-shake gate (esbuild minified + gzip)

- `purechess/core`: 2,308,027 B raw → 83,195 B gz
- `purechess` (full): 2,308,027 B raw → 83,195 B gz
- `chessops` (full, `import { Chess } from "chessops"`): 17,008 B raw → 5,336 B gz
- Core is **15.6× larger** than chessops (gate wants ≥30% smaller): the Black
  Magic tables (`dist/rookMagic.js` ≈ 3.2 MB raw, statically imported by
  `attacks.ts`) dwarf everything. chessops computes attacks table-free.
- Dead-code check ✓: `parsePgn` and Chess960 bytes absent from the core
  bundle (`sideEffects:false` + exports map tree-shaking works).

## Verdict

The measurement rig is sound and the parity-first methodology works (it
caught four distinct purechess defects the existing test suite missed).
Performance gates that passed: sliding attack speed (≈3×) and PGN streaming
(≈2.2×, heap parity). The chessops→purechess workstation migration
(`purechess-adopt`) is **blocked** until:

1. castling movegen/perft correctness (`makeMove` normalized-dest handling +
   internal `perft` movegen),
2. en-passant FEN round-trip (`makeFen`/`parseFen` ep-square agreement),
3. `makeSan` castling rendering for normalized dests,
4. the replayed-position dest/terminal defect,
5. bundle size (lazy magic-table loading / code-splitting)

are fixed and these gates go green.
